# Generated Instances — Experimental Dataset

Benchmark problem instances for the Hash Code 2017 "Streaming Videos" solver,
generated by [`generate.py`](./generate.py).

## Motivation

The four official Hash Code datasets (`me_at_the_zoo`, `trending_today`,
`videos_worth_spreading`, `kittens`) each test one combination of size,
topology, and demand pattern.  To properly evaluate the solver across the
parameter space — and to compare strategies like `global` vs. `per-cache`,
eviction on/off, or swap on/off — we need a larger, more controlled set of
instances where each structural axis is varied independently.

This dataset provides **12 instances** spanning four difficulty tiers
(tiny → large), with systematic variation of the four axes that most affect
how the greedy solver behaves.

## Quick start

Regenerate all instances (deterministic, seed `2017`):

```bash
python3 generated_instances/generate.py --out-dir generated_instances
```

Solve one:

```bash
python3 solution.py generated_instances/medium_tight_capacity.in /dev/null
```

Solve all and collect scores:

```bash
for f in generated_instances/*.in; do
    echo "=== $(basename $f)"
    python3 solution.py "$f" /dev/null 2>&1 | grep "score ="
done
```

## What varies across instances

The 12 instances systematically vary four axes that affect how the greedy
solver behaves:

| Axis | What it means | Low end | High end |
|---|---|---|---|
| **Network density** | Fraction of caches reachable by each endpoint | 0.15 (`large_sparse`) | 1.0 (`*_dense`, `*_full_mesh`) |
| **Capacity pressure** | `total_capacity / total_catalog` | 0.30 (`large_sparse`) | 1.81 (`tiny_dense`) |
| **Demand skew** | Zipf exponent over video popularity | 0.0 (uniform) | 2.0 (`medium_heavy_skew`) |
| **Scale** | V × E × C | 10×4×5 (tiny) | 500×50×25 (large) |

### Why these axes matter

- **Network density** controls how much overlap exists between caches. In a
  sparse network, each cache serves few endpoints and the problem decomposes
  into nearly-independent knapsacks. In a full mesh every cache competes with
  every other for the same endpoints, so the iterative `best_latency` updates
  and the eviction pass make a real difference.

- **Capacity pressure** (ratio of total cache capacity to total video catalog)
  determines whether the challenge is *what to leave out* (tight) or *where to
  place copies* (loose). When capacity ≈ catalog, nearly everything fits and
  the score ceiling is close to 100%.

- **Demand skew** (Zipf exponent *a*) models how concentrated user attention
  is. At *a* = 0, every video is equally popular. At *a* = 2.0, a handful of
  viral videos dominate traffic, which means a few key placements yield most
  of the score and the long tail of niche videos is irrelevant.

- **Scale** affects raw runtime and whether per-round cost stays proportional
  to actual demand (as the solver intends) or blows up.

## How the generator works

The generator ([`generate.py`](./generate.py)) works in three steps:

### 1. Specification via `InstanceSpec`

Each instance is defined as a dataclass `InstanceSpec` that captures all the
knobs:

- **Structural**: `V`, `E`, `C`, `R`, `X` (the five header values).
- **Topology**: `density` (fraction of caches each endpoint connects to),
  `k0_fraction` (fraction of endpoints with no cache connections).
- **Latency**: min/max ranges for datacenter and cache latencies.
- **Demand**: `zipf_a` (Zipf exponent for video popularity), `video_coverage`
  (fraction of videos that actually appear in requests), `request_min`/`request_max`.

The 12 specs in `INSTANCE_SPECS` are hand-designed to span the parameter space
above.

### 2. Generation via `generate_instance(spec, rng)`

For each spec, the generator:

1. **Draws video sizes** uniformly from `[size_min, size_max]`.
2. **Builds the network**: for each endpoint, picks `K = density × C` caches
   uniformly at random, assigns each a latency drawn from `[cache_latency_min,
   min(cache_latency_max, L_D − 1)]` (enforcing the spec constraint `L_c < L_D`).
   Endpoints in the `k0_set` get `K = 0`.
3. **Generates request descriptions**: picks `(video, endpoint)` pairs without
   repetition, with video selection weighted by a **Zipf distribution**. When
   `zipf_a = 0`, all videos are equally likely; higher values concentrate
   demand on a few "viral" videos. Request counts are drawn uniformly from
   `[request_min, request_max]`.

All constraint ranges from the problem statement are enforced:
- `1 ≤ S_i ≤ 1000`, `2 ≤ L_D ≤ 4000`, `1 ≤ L_c < L_D`, `0 < R_n ≤ 10000`, etc.

### 3. Manifest

After generating all `.in` files, the script writes a `manifest.csv` with
computed statistics (capacity/catalog ratio, average K, total requests, etc.)
for easy import into spreadsheets or analysis scripts.

### Reproducibility

The generator uses a single `random.Random` instance seeded with `--seed 2017`
(the default), so re-running always produces identical files.
